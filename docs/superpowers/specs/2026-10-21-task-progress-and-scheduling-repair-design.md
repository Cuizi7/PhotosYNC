# 任务状态与推进效率修复设计

基线：0.3.0 beta2，`58b9559`。用户已批准本线程 v2 原型：每任务一行小字、名称与数量同一行，各自同宽同高纯色进度，无渐变，分任务 hover。此次新增范围是运行日志反映的调度/错误分类问题，证据见[只读诊断](../../validation/2026-10-21-beta2-runtime-task-audit.md)。

## 目标

让未完成的任务持续可辨认，正常批次让出不会变成“等待恢复”；消除通知分类中的全队列一分钟停顿和确定性超限的无限重读。状态必须反映修复后的真实运行事实，不能靠延迟显示掩盖卡顿。

## 执行与展示事实

- 保持两条异步工作流程可以重叠；视觉 catalog 与首次 Live Photo catalog 继续串行；实际 Photos 写入仍全局串行。
- 现有瞬时 activity 增加“有到期且获准继续的排队工作”事实。排队/执行/真实等待/结束分别表达，不使用 `Task != nil` 或单纯 `pending > 0` 冒充可运行。
- 正常批次切换、已获准任务等待下一 tick 属于可运行：视觉或历史识别使标题保持“正在准备”；实际补齐和来源同步属于“正在同步”。未来重试期限、资源排空、未核实依赖、权限/上下文问题不能被误标为可运行。
- 六个用户标题及安全优先级保持：阻断错误/权限、暂停、未知写入优先；有健康任务推进时局部来源不可用保持独立提示。
- 未完成任务行以任务生命周期存在，固定先视觉、后 Live Photo；执行、正常排队、暂时等待之间不删除再插入。真实结束才移除，取消/来源停用按现有任务适用性撤下。
- 等待/暂停时保留已有数量，停止动画；在同一行显示简短状态，hover 给原因。不能继续显示“正在…”却隐藏真实阻塞。不使用显示防抖作为业务状态修复。
- Live Photo 的识别计数按图库项目；实际补齐阶段使用不确定进度，不能沿用识别阶段的 100% 当成补齐进度。

## Live Photo 通知与退避

- “通知尚在分类”是明确的准入延后，不等同于目标内容已改变。新物理读取等已有分类完成后准入；已完成读取先等待分类，再核实 ticket/context/完整 Live Photo descriptor，允许确认无关的事件保留结果。
- 等待复用现有 producer 串行队列：在同一 submission lock 下捕获事件水位并排入一个 FIFO 标记，只覆盖排入前的事件。标记只确认分类已走过该批次，不建立候选快照、不触发全库重建、不成为第二个分类器。每次读取最多等待一次，逻辑等待上限 5 秒（单调时钟，可注入）；不能把无超时的 `candidateSnapshot()` 当作有期限的等待。
- 5 秒到期返回 classification-pending 延后，取消返回 cancellation；两者均不接受观察结果、不设置全队列 60 秒冷却。迟到的标记只结束自身，不触发新的读取或提交。已完成的 raw lease 保留到校验/消费者结束；取消仍在进行的 raw request 则沿用既有实际结束后释放规则，不能以逻辑超时释放物理槽位。
- 标记完成后出现新通知：若仍待分类，返回 classification-pending；若已经分类，重新核对 ticket 和完整 descriptor。目标确切变化/删除丢弃旧观察并刷新目标；unknown coverage、上下文/权限失效转入相应恢复，拒绝旧观察。metadata 和入库前守卫再次遇到 pending 也走 typed 延后，不退回通用错误的一分钟冷却。不循环等待通知安静，不将视觉 `inputUnchanged` 当作 Live Photo 内容证明。
- 目标 revision/资源集合变化时丢弃旧观察，先刷新该资产描述再处理新修订；删除、未知覆盖、权限撤回继续 fail closed。
- 分类完成/描述刷新通过现有事件和 tick 唤醒；该类正常竞争不设置整条 Live Photo 队列 60 秒冷却。网络等单项失败保存在单项期限中；真正全局无法继续的故障才设置全局等待。
- 补齐仍等待未核实的潜在完整目标。修复识别的推进能力，不通过放宽这个防重复创建规则提速。

## 确定性解码限制

- 仅将经 typed error 确认的 `decodedResourceLimit` 作为同修订的自动重试暂停项；不扩大到所有读取/容器错误。
- 保持 schema v11 的 CHECK 和 `failure_kind='photos_read'` 不变，表示该失败可隔离；在 `fingerprint_task` 中仅将 `next_retry_at=Date.distantFuture` 作为 typed 解码超限的保留编码。不能新增持久枚举值，也不解析历史错误字符串回填。当前产品没有其他 fingerprint task 写入该期限；旧记录下次真实尝试得到该类型后转为暂停。
- 写入仍验证任务的 context、修订、generation 和输入契约。自动选择明确排除上述组合；显式重试仅重开当前上下文中与有效表示精确匹配的该组合，将期限置为当前时间。普通临时失败使用有限重试期限。候选隔离仍沿用 `photos_read` 的现有谓词，不能将保留项放回视觉判重候选。
- 健康表示仍可发布；“可发布”不等于所有任务已结束。用当前有效保留记录计算独立的需处理照片数（按 asset 去重），不把全部读取错误当作人工处理。仅剩保留项时标题为“需要处理”，视觉任务行保留数量、标明“N 张需处理”、进度停在真实比例；有健康工作时继续显示实际运行标题，并保留该局部提示。hover 说明超出解码预算、已停止自动重试及“立即扫描”可重试；不能显示自动等待或同步完成。
- 精确资源修订/解码输入契约变化自动重开；用户明确点击“立即扫描”时可重新尝试一次。启动、唤醒、普通 tick 不重开确定性限制。
- 512 MiB 解码预算、原资源编码预算及源文件只读保持；不通过提高额度解决。

## 轮询、诊断和 UI

- `current()`/活动和进度投影只读已发布事实及必要的轻量队列摘要，不能触发 PhotoKit catalog/snapshot 工作。真正判重、发布和写入准入仍重新验证 generation/context。
- 没有到期工作时利用已有下一期限和变更通知跳过空消费切片；保留通知、授权变化、显式扫描和暂停恢复的及时唤醒。
- Live Photo 日志补匿名资产 handle、阶段、原因类别、相关事件、读取/分类等待/核对耗时及字节数；30 秒有工作才汇总，失败/等待原因改变时记录。不得记录私人文件名/原始资产 ID，不新增空转日志洪流。
- UI 使用已批准 v2 原型，320pt 菜单；每任务一行，统一 5pt 纯色轨道。已知比例从左填充；未知使用同色短段移动。hover 按任务说明计数、iCloud 流量/缓存、续跑及 Live Photo 对旧单项的影响。

## 验收

使用可控门闩/时钟覆盖通知分类与读取交错、短批次间隙、未来重试、确定性限制、暂停和未知写入。复现必须先失败；修复后证明不丢有效结果、不接受过期结果、不热循环、不增加物理并发。原生浅深色验证单/双任务及 hover，标题/行在正常批次间隙稳定，真实阻塞及时显示。

本次涉及 PhotoKit 时序、持久失败分类与资源行为，使用完整深度评审、独立 tester 和 `full` 验收。真实运行复测需明确使用修复后的构建；未做的系统边界保留为缺口。2026-10-22 用户批准串行实施；开发与验证在隔离工作树进行，不修改运行中的应用或生产库。
