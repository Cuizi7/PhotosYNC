# 云端 Live Photo 处理与同步状态修复

日期：2026-10-21。基线：`82a80e8`（0.3.0 beta1）。状态：修复方案，待审阅；不含 UI 排版重设计。

## 目标与范围

历史 Live Photo 身份识别能够按需读取 iCloud 原件，已有未完成记录继续处理；用户从菜单、设置和详情中看到相同、准确的同步状态。沿用原生界面和既有 hover，不增加下载开关或独立下载页面。

本轮只修改读取生命周期、必要的任务调度与只读进度事实、状态投影和相关文案。来源严格只读；精确配对、验证后定向清理、标题不作保护、成功历史、用户删除保护和未知提交阻断均沿用已批准规则。最低 macOS 13，Universal arm64/x86_64，无新运行时依赖。规划不授权新的真实图库写入、生产库维护、安装、发布或远端操作。

## 1. 云端资源与续跑

- 历史识别和逐项重试均允许现有公开 PhotoKit 原资源请求联网；由系统按需提供文件。下载是分析/配对的内部步骤，不形成用户状态、独立进度或设置项。不承诺系统缓存原件的驻留时间。
- 不重置固定任务键 `live-photo-initial-identification-v1`，不清空数据库，不重跑已完成且资源版本未变化的项目。beta1 的 `queued` 和 `unresolved` 记录直接沿用；完成标记只表示首次清单与本轮尝试结束，不能直接决定用户可见“同步完成”。
- 未变化的确定检查结果继续复用。失败项目独立恢复，其他项目继续；没有对应另一半但已成功保存的单项，不因等待一个尚不存在的文件而阻止“同步完成”。
- Live Photo 临时原资源仍共用 **512 MiB** 总预算、至少 **128 MiB** 磁盘保留和既有物理并发上限。不提高全局读超时、不建立产品级原片缓存、不转码、不放宽精确身份或版本核对。
- Live Photo 原资源请求单独使用 **600 秒请求期限、610 秒外层逻辑等待上限**，替代对此路径直接套用 60 秒默认值。期限/调用任务取消至多发送一次 `cancelDataRequest`；实际完成回调之前仍占用物理槽位、临时文件和字节预算。取消返回不等于物理结束；回调丢失时继续保留占用，不能新建 reader 绕过。测试注入短期限与门闩，不实等十分钟。
- 用户暂停阻止后续读取与提交，已发出的读取可以结束；不能承诺立即停止网络或清掉系统缓存。暂停/权限变化后不得用晚到结果推进新的读取、创建或删除；已经成功的实际提交仍按原规则结算。
- 暂时读取失败按现有逐项 60 秒期限恢复，不在每秒 UI tick 中重试。明确单资源超上限或确定无法自动解析的项目保留为未完成，暂停该版本自动重试，避免反复下载同一大文件；资源变化或用户主动“立即扫描”才重新尝试。补齐/验证同时持有的固定工作集超过 512 MiB 时也暂停该版本自动重试；例如两份各 300 MiB 的必需资源，不能误报为其他任务暂占预算。只有其他任务暂占或物理资源竞争属于正常等待。未知原因按可重试处理，不从错误文案猜测。

长读取仅在 context、权限及目标资产 revision/资源选择仍有效时保存观察结果。复用已有按资产读取票据和变更失效机制：覆盖完整、明确与该资产无关的增删不使已完成读取作废；目标变化、删除、未知变更覆盖或权限/图库变化仍拒绝。协调器在写观察前再次核对目标描述和持久 revision。此调整只适用于只读身份观察，创建、验证和删除前的 generation/版本守卫不放宽。

## 2. 调度与实时事实

保留一个 runtime、一个 gateway 和一个实际 Photos 写入槽位。视觉索引与 Live Photo 原资源工作分别由 runtime 持有一个有界任务，普通来源扫描继续沿用现有任务；只解除慢原件读取对视觉索引、变更核对及状态发布的串行阻塞，不增加物理并发。两类 catalog 枚举仍由同一个 runtime 串行入口调度，视觉 reconciliation 与 LP 首次枚举不得重叠或互相替换唯一 catalog session；不引入多 session 框架。

Live Photo 每次处理最多一个历史资产，再最多推进一个组操作；完成后交回已有 tick。一次历史枚举仍分页持久化，不重复枚举已完成任务；枚举期间允许查询进度。长读取期间仍能刷新状态、接收暂停/授权变化，并推进其他有资源准入的工作。已有 actor 的防重入、版本守卫和组预留继续生效。

runtime 发布明确的“正在执行／等待恢复／空闲”事实，而不是让 UI 从 `activeWork`、历史错误文本或 `phase=completed` 猜测。视觉索引 coordinator 同样显式报告 reconciliation、读取/计算是否在执行，不能只看持久 `IndexProgress.state`。正在建立任务对象、到期前的队列以及旧错误记录，不等同于实际有工作推进。失败原因保留类型与诊断详情；内部标识和系统原文不进入常显文案。

原资源 reader 提供只读准入快照，区分可读、忙、取消排空及长期未结束；排空期间 tick 不重复调用同一读取。其他资源竞争沿用 5/5/15/15/60 秒 deferred 曲线；它不污染文件失败/云端失败重试计数。准入快照只是提示，实际请求仍须重验容量和权限。

## 3. 六种整体状态

| 文案 | 适用条件 |
| --- | --- |
| 正在准备 | 启动恢复或必要的图库分析正在推进，当前没有实际来源同步/补齐工作推进 |
| 正在同步 | 来源扫描、判重、导入或 Live Photo 补齐/验证/定向清理有实际工作推进；可以同时进行图库准备 |
| 等待恢复 | 剩余工作当前均在等自动恢复、资源可用或重试期限；另显示简明原因 |
| 已暂停 | 用户主动暂停；在途结果仍按原生命周期结算 |
| 需要处理 | 缺授权、无可用配置、不可恢复的初始化/存储问题，或只剩不能自动处理的项目；另给出原因和已有可行动入口 |
| 同步完成 | 本轮工作结束，没有尚未执行的检查、自动重试、实际提交或未确认结果 |

优先级：全局需人处理的阻断 → 用户暂停 → Photos 提交结果未知的安全等待 → 有实际同步工作 → 有实际准备工作 → 局部需人处理的问题 → 自动恢复等待 → 同步完成。启动尚未取得状态时显示“正在准备”，不能先报完成或未授权。

- 来源离线但图库分析仍在执行：显示“正在准备”；健康来源或补齐仍在推进：显示“正在同步”。来源问题始终单列，不能隐藏，也不把后台活动误报成全部停工。
- 提交结果未知显示“等待恢复”，原因是“等待‘照片’确认结果，新的保存已暂停”；不暗示用户可以通过重试导入消除未知状态。读取/计算仍可继续，但不能掩盖此全局写入阻断。
- 已验证完整目标且出于信息保护保留原单项，是正常保留结果，不能永久显示“等待清理”。仅有完整保存证据、但验证未通过的目标，仍是未完成。明确失败的清理与受保护信息保留分开；未知删除仍阻断。
- 没有启用来源但仍有 Photos-only 历史工作时照常显示工作状态；历史工作结束且没有启用来源时，“需要处理”附“请添加或启用来源目录”。通知权限/日志告警等非阻断提示不提升整体状态。

## 4. 进度、常显文案与 hover

菜单与设置复用同一份状态、进度和详情投影，不各自判断。只修改现有状态区域和必要的详情内容，不采用此前生成的 UI 草图，不增加导航或选项。

- 前两种状态展示进度；小字仅使用 **“正在建立视觉索引”**、**“正在配对 Live Photo”**。有实际活动的两项各占一行，顺序固定；两者均未活动时不造“正在”文案。初始化仅显示不确定进度，普通同步沿用来源文件进度，不再细分“保存到照片”等步骤。
- 视觉索引使用 `已分析 X / Y 张`；历史资源识别使用 `已处理 X / Y 项`。后者是检查结果确定的资产数，不是找到的配对数；读取失败不进分子。不把照片、视频、表示、来源文件或配对组相加为总百分比。
- 总量未知时只显示 `已分析 X 张`／`已处理 X 项` 或不确定进度，不显示零总数、假百分比或 ETA。历史检查完成但仍在组验证/清理时使用不确定进度，不沿用检查的 100% 冒充整个配对完成。新增和变化可使总量增加。
- 用户常显不再看到“已清点／已识别／待核实”“历史识别已完成，部分项目待核实”“正在下载 iCloud 原件”“新增到照片”等内部阶段。云端不可用或其他真实阻碍需要显示原因，但不展示原片下载步骤或下载百分比。
- “等待恢复”显示诸如“来源目录暂不可用，连接恢复后自动继续”“部分项目暂时无法读取，稍后自动重试”；“需要处理”显示具体原因及授权、添加来源、主动重试或查看诊断等已有入口。文件/来源局部问题在其位置保留，不被进度覆盖。
- hover 解释目的和口径：视觉索引用于避免重复导入；Live Photo 工作核对原文件中的配对关系并补齐完整效果；必要时从 iCloud 获取原文件，会产生流量，系统可能保留本地缓存；结果保存，重启继续未完成项，常规启动不会重复分析未变化的成功结果。
- hover 仍支持点按固定、键盘打开及 Escape 关闭。等待确认、失败原因和需要用户执行的动作不能仅藏在 hover。资源标识、错误码、重试次数、一次性标记与系统详情留在诊断中。

## 5. 数据与兼容

保留 schema v11 和四种来源文件状态；不为展示状态写入新的持久状态机。历史识别汇总增加未处理、到期重试和需处理数量，复用现有索引做聚合，不按每秒轮询逐项解码全库 payload。

逐项暂停自动重试复用 `status='unresolved' AND next_retry_at IS NULL`；历史 beta1 的 unresolved 均已有重试期限，继续自动重试。记录接口显式接收自动重试期限或需处理决策，查询不能把 NULL 当作立即到期。主动重试只重开这些未完成项，不改已检查、完成时间、成功历史或实际提交证据。原错误仍保存在现有 observation payload。

组的保留、工作集超限和其他失败使用现有 operation payload 的可选类型字段区分，旧 payload 缺字段仍可解码；不新增表/列。需主动重试的组复用既有暂停重试期限，未知提交不得被重新尝试接口解除。保护性保留仍是正常结果，不能与资源超限混成同一种“已保留”。

内部 `GlobalStatus` 增加准备并移除未配置状态；其余 raw value 可保留以缩小改动，但用户文案严格只有上述六种。准备复用现有运行中图标标记，不重新设计品牌图标；未配置通过“需要处理”及原因表达。同步更新 demo/GUIQA 和受影响的穷举断言。

## 6. 验收

1. fake 云端原件只有 `allowNetwork=true` 才成功；首次识别和旧 unresolved 重试均能成功，重开库后不重扫已完成项目。
2. 超过旧 60 秒仍在读取的请求不会被提前丢弃；新期限、调用取消穿过非结构化 Task、同步回调/迟到回调、共享预算满、单资源/组固定工作集超限、磁盘保留、物理槽位释放均有门闩验证，不依靠随意 sleep。
3. 慢 Live Photo 请求期间视觉任务/来源扫描/变更核对和状态发布仍可推进；两种 catalog 枚举的两种启动顺序均不互相覆盖会话；无关新增资产不丢身份读取，相关变化/未知覆盖仍拒绝。暂停、恢复、授权撤回及重启不产生第二个物理请求或新的 Photos 写入。
4. 六状态表覆盖并发、局部离线、等待期限、未完成队列、首次标记已完成但仍有失败、未知创建/删除、保护性保留、无来源及首次启动；不能从未知或单次查不到推断成功/失败。
5. 菜单、设置和 hover 在相同 fake 快照下状态/数量一致；总量未知、多任务、暂停及问题状态不虚报进度。明暗原生离屏证据与真实系统交互分别标注，不启动生产应用。
6. 最终集成由 deep_reviewer 与 tester 验收；资源/并发/索引进度行为变化使用 canonical `--scale-profile full`。真实 iCloud 读路径需要针对性只读验证；实际下载前先确认可接受的资产范围/流量。未执行不得以 fake 或先前本地素材 QA 代替。

实施时更新运行时契约、完整 Live Photo spec 和 README 中相冲突的当前说明；保留 beta1 发行与验证记录作为历史事实。本轮不改版本号、不自动打包或发布，后续发布另行处理。
