# PhotosYNC：完整 Live Photo 导入与补齐

日期：2026-10-21。状态：已批准并在开发分支实施，验收进度见[验证记录](../../validation/2026-10-21-live-photo-completion.md)。源码基线：773a493；迁移前数据库 schema v10，开发版 v11。

## 1. 目标

默认将配套照片（HEIC/JPEG）与 MOV 导入为 Photos 中一个原生 Live Photo，保留原资源的静态画面、动态和声音，不转码，不新增设置选项。

采用统一的保存、补齐和清理流程，覆盖 PhotosYNC 导入的项目及图库原有、能够精确确认配对的照片和视频：

| 资源情况 | 行为 |
| --- | --- |
| 只有照片或 MOV | 先按普通照片或视频保存、判重，记录可取得的配对身份 |
| 两部分均可取得 | 优先一次创建完整 Live Photo |
| 一部分已单独保存，另一部分后到 | 创建或复用完整 Live Photo，验证后清理被替代单项 |
| 配对有歧义或另一半暂不可读 | 保存当前可用内容，保留旧项，后续继续识别 |
| 完整目标已创建，验证或清理未完成 | 仅恢复未完成阶段，不重复创建 |

以单个文件夹为导入批次：先完成直属文件枚举及本轮有界配对识别，再放行该文件夹的导入。子文件夹独立处理，不等待整个来源目录树；已识别的完整配对优先一起提交，只有一半的按单项保存。枚举结束后才到达的文件在后续扫描补齐。

目录枚举失败或中断时不放行该目录，按现有规则重试；单个文件读取失败不阻塞同目录健康文件，未能读取的身份保持未知。其他已完成目录可以继续。清理范围仅限精确确认且内容、受保护信息已保留的旧单项，包括非 PhotosYNC 导入的资产。来源目录始终只读。

## 2. 平台能力与验收目标

使用同一个 `PHAssetCreationRequest` 添加 `.photo` 和 `.pairedVideo`，`shouldMoveFile = false`。公开 API 没有文档化的方式向普通资产原位追加另一半，因此补齐通过创建完整资产再替代旧项实现，资产 ID 会改变。

验收要求 Photos 显示原生 LIVE 项目，可展示照片、播放动态及原有声音，方向、时长、静态帧位置和资源身份正确。不合成原件没有的声音，不承诺恢复备份未保存的编辑历史或关键照片选择。

已完成只读可行性验证：12 对 NAS 文件的配对 ID 一致，MOV 均有实际 still-image-time 样本；AVFoundation 识别对照 15/15、排除执行沙箱影响后的 PHLivePhoto 加载对照 14/14 符合预期。加载对象的 size 为 0，因此这些结果仅证明识别与资源配对，不能代替真实导入、解码、播放或 iCloud 验收。证据位于 `work/livephoto-native-feasibility-20261020/` 和 `work/livephoto-pair-feasibility-20261020/`。验证宿主为 macOS 27.0.1；macOS 13 仅做过部署目标编译。

API 依据：[添加原始资源](https://developer.apple.com/documentation/photos/phassetcreationrequest/addresource(with:fileurl:options:))、[配套视频](https://developer.apple.com/documentation/photos/phassetresourcetype/pairedvideo)、[加载 Live Photo](https://developer.apple.com/documentation/photos/phlivephoto/request(withresourcefileurls:placeholderimage:targetsize:contentmode:resulthandler:))、[修改既有资产](https://developer.apple.com/documentation/photos/phassetchangerequest)。

## 3. 配对、发现与资源读取

### 首次运行的历史识别

新版本首次运行时，内置一次可断点续跑的全库识别任务。枚举当前系统图库授权范围内的全部照片和视频，包括其他途径导入、没有 PhotosYNC 记录的资产；同时核对全部本地历史记录，启用来源按目录扫描补读源文件身份。范围不按文件名、时长或固定样本清单筛选。停用/移除来源不启动源读取，不可访问的图库范围不宣称已覆盖。

任务在本 App 数据库中记录完整 Live Photo、静态组成部分、动态组成部分、已检查未发现配对标识、待核实等识别结果，并保存配对 ID、识别版本和资源 revision。“未发现标识”不等于证明原本不是 Live Photo；只有精确确认后才登记配对。识别本身不改变 Photos 资产类型，也不执行导入或删除。

全量清点和元数据识别分批执行，复用现有资源预算、调度和 Photos 变更流。持久化图库身份、固定功能迁移标识、任务状态、扫描进度、逐项结果及完成时间；任务标识不随 App 常规版本号变化。中断后仅续跑未完成部分。全量清点及逐项本轮识别尝试结束、待核实项已入队且变更已衔接后，事务性标记本任务完成；此后重启或常规升级均不得再次完整执行。待核实项只按项重试，新增/变更由增量流程处理，不清除一次性完成标记。切换图库或权限范围扩大时仅补足尚未覆盖的新图库/新范围，返回已完成图库不重跑；扫描期间的变更须纳入核对，不因游标移动漏项。

全库历史分析和旧未完成项重试允许按需获取 iCloud 原文件。原资源请求期限600秒、逻辑等待610秒，实际完成回调前保留物理所有权；共享512 MiB预算、128 MiB磁盘保留及既有物理并发不变。临时失败逐项60秒重试；确定无法解析、单项或本组固定工作集超限暂停该版本自动重试，资源变化或用户主动“立即扫描”重新尝试。启动／唤醒的自动扫描不重新打开这些暂停项，也不重置首次完成标记。一次性完成只代表首次覆盖及尝试结束，未完成项继续逐项恢复。

历史原资源工作由独立且唯一的任务推进，每轮最多一个资产和一个组操作；视觉与历史 catalog 枚举保持串行。身份观察允许覆盖完整的无关资产变化，目标变化、删除、未知覆盖或授权撤回仍拒绝；实际 mutation 的版本及 generation 守卫不放宽。整体六状态及进度见[云端与状态修复设计](2026-10-21-cloud-livephoto-status-repair-design.md)，菜单／设置只显示“已处理 X / Y 项”，失败不进分子。

精确确认的历史配对进入统一补齐流程，包括两部分仅存在于 Photos 的情况。首次清点及对可读资源的一轮识别结束前，所有完整 Live Photo 新建入口（包括新来源配对）均等待，避免尚未发现已有完整资产就重复创建；已配齐资源不因等待而拆成两个单项提交。未知候选只有经可靠身份/冲突证据排除才视为无关；无法排除且可能是已有完整目标的资产继续阻止该组新建，不能仅凭改名或缺失时间忽略。普通单项保存仍遵循目录批次与判重规则，不等待全库历史任务。历史单项的成功记录保留，不重置为未导入。

历史盘点和仅有 Photos 成员的组不依赖启用来源，仍受图库授权、全局暂停及提交未知阻断约束。现有暂停入口在这类任务存在时也可用；来源扫描保持自己的启用条件，不增加独立开关。

### 配对与资源规则

- 照片读取 Apple Maker Note 配对身份及辅助标记；MOV 读取非空 QuickTime ContentIdentifier 和实际 still-image-time 样本。两侧身份、角色和版本匹配后，再通过原生资源验证。格式标识需覆盖系统差异。
- 文件名、目录、时间、尺寸和视觉相似只用于找候选，不能独立证明配对或授权删除。缺少标记不等于普通媒体；同 ID 的不同编辑/导出版本不能任意拼接或清理。无法确定版本时保留歧义。
- 配对身份可来自来源扫描或全库历史识别，允许跨启用来源、来源与 Photos、Photos 内部配对。先使用已确认身份索引与成功历史定位，再利用文件名、资源角色、拍摄信息及已有视觉候选补充发现，读取原资源确认。停用来源不启动源读取，其已保存的图库资源仍可参与。
- 缓存已确认身份并绑定资源 revision，通过 Photos 变更使其失效。不建立全库视频指纹索引；原文件按任务及预算逐项读取，不预先下载整套原件；改名、无关联记录、信息不足或云端暂不可读可能延迟发现，不能据此断言另一半不存在。
- 无旧项需要替代时可使用源 URL。准备清理旧项时，新目标必须实际使用该精确 Photos 资产的原资源；配对 ID、成功历史或未变的 size/mtime 不能证明当前源文件与旧资源相同。
- 源文件不缓存、不改名、不转码。Photos 原资源复用有界临时存储：所有同时保留的输入与验证文件合计不超过 512 MiB，保留至少 128 MiB 可用空间，先预留预算再读取。MOV 不走图片解码管线；超限或读取失败保留单项并说明补齐受限。

## 4. 状态、判重与持久化

保留文件四状态 `pending/importing/imported/skipped`。文件保存成功与整组 Live Photo 完成分别记录；补齐失败不撤销已有成功，不清空成功历史。汇总仍按源文件计数，两份资源成功保存计两个文件。单纯缺半不算错误，也不持续占用活动工作状态。

配对身份在普通判重前登记。静态视觉重复不能代表 Live Photo 完整；即使文件被普通规则跳过，也保留配对观察。完整候选须核实 subtype、资源角色、拍摄身份和版本。复用已有完整目标时，未由本 App 提交的文件记为有目标证据的 `skipped`，不伪造成功回调或 `success_id`。

配对模型分为三类：资源观察（身份、角色、revision）、Live Photo 组（成员、版本、完整目标、替代历史）、操作记录（固定输入、旧资产清单、属性快照、创建/验证/清理阶段及恢复证据）。当前使用 schema v11，迁移保持事务化并同步两处 schema 定义；新增可选识别字段在正常扫描时补读：即使文件属性未变、已 imported 或 skipped，也须先补齐尚未完成的配对识别与组登记，再走已有记录的快速跳过路径；不清空成功历史、不重复提交单项，迁移不访问媒体。

目录放行条件覆盖本轮新文件及历史 pending/retry 的新提交，不能被共享 drain 绕过；已提交请求仍正常接收结果和恢复，暂停、重启或目录变化后须重新核实放行条件。跨目录成对提交时，两侧源目录均须完成各自批次。目录就绪在异步边界及提交前复核；目录放行不等于来源扫描完成，来源级缺失记录和诊断清理仍须满足原有完整遍历条件。

组操作事务性预留源成员，单文件 drain、retry、recoverImports 排除这些成员。已有单文件 importing/unknown 先由原路径核实，组不得抢占。启动先恢复组操作及全局未知提交阻断，再开放普通提交；即使成员全已 imported，仍须恢复组任务。预留按持久阶段事务性释放。

成对新建共享一个 attempt、placeholder 和成功结果，两行同时记账；明确未提交才一起恢复 pending。补齐已成功单项时，旧 imported 和成功关系保留，仅未保存成员跟随实际新提交变化。Runtime 同时展示组内待验证、待清理或未知任务，避免文件已保存掩盖未完成工作。

源及图库资源复用同一套身份识别逻辑；专用协调组件推进组操作；store 维护事务和首次识别任务的进度；gateway 执行 PhotoKit。复用现有调度、变更流和唯一 Photos 提交执行器，历史任务不另建业务状态机。无源文件成员的组同样持久恢复，但不伪造 file_record 或增加源文件导入计数。

## 5. 创建、验证与清理

1. **预检并记录意图：** 固定图库上下文、资源版本、精确旧资产 ID 和属性/相册快照；排除歧义。各异步边界复核暂停、来源启用、权限和版本，在实际 mutation 前执行 `beforeMutation` 守卫。
2. **创建或复用完整目标：** 一次加入照片和配套视频，保留可确定的属性及普通相册关系。已有精确完整目标时直接验证。
3. **先记成功，再验证：** 保存明确成功证据，核实目标 subtype、两项资源、身份、播放对象及输入音轨保留情况。验证失败保留新旧资产，不撤销成功事实。
4. **复核并清理：** 确认新旧资产未变化且满足下列准入条件，持久化精确清理意图后，另发 PhotoKit 删除请求。只处理被替代单项，不删除完整 Live Photo、不清空“最近删除”。明确成功后记录替代关系；明确失败或未知结果保留未完成阶段。已验证目标且因受保护信息保留旧项是正常保留结果，不持续显示待清理，不反复弹窗。

清理必须同时满足：

- **原资源已保留。** 新建使用旧资产的准确原资源并绑定 revision 和成功提交证据；复用完整目标时，定向、按预算流式逐字节比较对应资源。不同、读不全、超限或 revision 变化均保留旧项。不计算或持久化内容哈希，不扩展为全库内容判重。
- **编辑及额外内容可保留。** 存在 adjustment data、额外资源、版本歧义或无法映射内容时保留旧项。
- **其余受保护信息已知且已保留。** 逐类检查日期/位置、收藏/隐藏、评分、说明/关键字、普通相册及编辑/额外资源，区分已知为空或不适用、已读且可保留、未知或不可保留。未知不能视为空；没有 adjustment 不证明没有文字信息。macOS 13–26 缺少部分公开字段时允许补齐，但保留无法核实这些信息的旧项。用户明确决定不保护标题：标题未知、不同或单独的标题变化均不阻止完整 Live Photo 验证后的精确单项清理，可能丢失旧标题；资源 revision 检查不放宽。
- **属性合并无损。** 普通可写相册取并集；任一收藏/隐藏则新建目标收藏/隐藏；日期/位置采用照片端，存在无法保留的用户改动或冲突时不清理。智能相册由系统重算。复用完整资产时不静默覆盖其用户属性来满足清理条件。

共享相簿资产不自动清理。人物、回忆、外部引用和原资产 ID 等未公开关联不在迁移保证内。PhotoKit 无跨设备比较版本并删除的原子接口；通过变更 generation 和最终重查缩小竞争窗口，发现变化即保留旧项，删除使用系统可恢复流程。

## 6. 恢复与用户删除

Photos 与 SQLite 无联合事务。创建、删除均先持久化意图；placeholder 不是成功，超时、取消或一次查询不到不是失败。唯一实际 PhotoKit 提交槽位同时约束创建和删除，未知结果阻断新提交，不能另建 gateway 绕过。

- 创建未知时不重建、不删旧；明确成功后恢复验证或清理。删除未知时保留目标与意图，取得充分系统变更和后态证据后才确认，不盲目重试。
- 事务已提交而日志未收尾时，以操作记录和准确后态幂等恢复，不重复计数或提交。
- 为已跟踪组保留 insert/update/delete 类型、资产 ID、图库上下文及游标/generation；在消费事件前，事务性写入删除事实和阻断。补齐现有 persistent replay 丢失事件类型的路径，不另建全库事件系统。
- 本功能清理操作与删除事件匹配只是关联线索，不能替代成功证据。外部删除完整目标或已关联单项时停止该组自动补齐/清理，保留历史，避免重新导入用户删除的内容。
- 游标失效、权限不足、无可靠删除事件的缺项进入待核实。身份和历史未知的删除不作推断。普通补齐受限不阻止无关联文件导入，实际提交未知仍按全局规则阻断。

## 7. 验证与交付

自动测试使用自制媒体、临时数据库和 fake Photos，覆盖：

- 同目录枚举及识别完成前零新提交，文件排列顺序不拆散配对；历史 pending/retry 不绕过等待；父子/兄弟目录独立、枚举失败重试、单文件失败隔离及扫描期间新文件后到。
- 首次全库识别覆盖无导入记录的资产及全部历史文件；中断续跑、完成标记原子落库、完成后多次重启及常规升级不重复全量执行、待核实仅按项重试、版本/revision失效、图库/权限变化、扫描期间增删、云端待核实与完成口径；仅 Photos 内配对、身份未知的云端完整候选、新来源配对不绕过首次盘点、盘点请求按需获取云端原件、无启用来源时运行与暂停、晚发现完整目标不重复创建。
- 两种先后到达、同批齐全、跨扫描/来源、永久缺半、Photos-only 原件和 iCloud 暂不可读。
- 身份错配/缺失、同 ID 多版本、同名异物、视觉相似误判；源 stamp 不变但内容不同；资源比较与预算边界。
- 新旧资产统一补齐、历史 imported/skipped 且属性未变的文件自动补识别、完整目标复用、组排他所有权和共享 placeholder、两行事务失败、全 imported 组恢复、文件计数。
