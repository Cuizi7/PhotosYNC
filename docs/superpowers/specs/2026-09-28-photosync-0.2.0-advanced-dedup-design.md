## 1. 目标与成功条件

导入前识别同一张照片的副本，包括改名、修改 metadata、压缩、缩小和常见格式转换。十万张级 Photos 图库应能增量维护索引，日常导入不重复读取全库图片、不逐张运行模型。

本版完全由机器决定，不增加人工确认、人工审核队列或相似照片浏览器。误跳过意味着用户照片没有导入，因此优先控制误跳过；比较成功但证据不足时导入。读取失败、索引未完成等属于未知，等待恢复，不能等同于“不是重复”。

用户已选择：SSCD Large；单模型候选检索与阈值判定；允许按需下载 iCloud 图像；首次索引就绪后才开始导入；更高分辨率副本仍导入；重新评估符合条件的旧疑似重复跳过项；持续维护 Photos 索引；同时覆盖 Photos 原始版和当前编辑版。2026-10-05 用户决定先采用 0.98 推进产品集成，停止进一步独立校准/封存研究，后续根据生产情况显式调整参数；保留生产诊断日志。这一决定替代原有研究统计通过前置，不表示原统计目标已获证明。

## 2. 范围与保留规则

- 高级内容判重用于现有支持范围内的静态照片。视频保持 0.1 的文件名与 metadata 策略，不增加视频抽帧、RAW 来源支持或 Live Photo 配对。Photos 中复合资产的可读静态照片表示可作为照片候选，不能据此判断其视频部分重复。
- 只读来源；Photos 只新增，不修改、替换、删除已有资产。仍提交来源原始 URL，`shouldMoveFile = false`，不重新编码导入文件。
- 不加入 pHash、第二个核验模型、服务端模型或独立向量数据库服务。指纹在本机生成、持久化和查询。
- 不将连拍、同场景、同人物等语义相似视为足够的重复证据。已确认的当前回归案例中，明显裁剪、明显调色、景深/虚化与明暗/对比编辑应保留为不同版本，判不重并导入；近邻街景中的车辆位置、取景变化也应判不重。2026-10-04 用户将 11 个合成信息看板用例移出当前测试范围，其旧标签保留为历史，不改成判重，也不从本次删例推导对所有文字差异的识别承诺。这些是具体案例的预期，不等于任意微小颜色或像素变化都必须判不重。
- 画面整体旋转 90° 是否构成需要保留的构图编辑尚未定案。B015、B017、B019 已移出当前回归集，先前审批不作为旋转规则的冻结依据；后续评估实际能力后再决定。正常解码时对 EXIF 方向的解释不因此省略，也不等于已决定用户主动旋转编辑的判重语义。
- 不假设单个向量分数能识别具体变换类型。运行时只使用已冻结的分数及可观测规则，测试覆盖已确认编辑与易混淆负例；旋转仅可作为未定预期的探索样本。当前采用第 7 节绑定的用户选定配置；原协议的误跳过率及分层召回统计目标尚未验证，不再作为本轮进入集成的前置。当前固定回归的内容与动作仍必须满足，实施者不得擅自删除已批准难例、改标签或临时加入第二模型掩盖限制。用户明确调整范围时应另存版本和原始理由，保留旧证据，并重新建立相应验收绑定；事后缩小范围不能冒充独立校准成功。若源文件本来就是图库当前编辑版的副本，应能匹配该表示；编辑版与原图判不重，不表示该编辑版自身的副本也要重复导入。
- 保留四种文件状态 `pending`、`importing`、`imported`、`skipped`；索引任务状态另行持久化，不新增文件审核状态。
- 成功历史不因来源停用、移除、文件变化或 Photos 删除而清空。未知 Photos 提交结果仍禁止盲目重试，同一时刻仅一个实际提交。
- 本文在静态照片判重、指纹存储和 Photos 图像读取范围替代 v1 的相应限制，其余运行时契约继续遵守 `docs/specs/2026-09-18-runtime-state-and-recovery.md`。

## 3. 判重流程与决策

### 3.1 指纹与候选

来源图片和 Photos 图片使用同一套方向、颜色、缩放、像素归一化与向量归一化处理，生成 SSCD Large 1024 维向量。模型、转换产物、预处理、向量格式和策略均带版本及校验值。当前批准的后端见 §7.1：FP16 Core ML、显式 Float32 输入/输出、ANE 优先与 GPU 降级；保持 sRGB、全画面 stretch 320×320，不中心裁剪，沿用 R2 的归一化参数，并因模型包改变生成新 fingerprintVersion。方向/颜色/宽竖图行为和固定回归已有研究证据，不能将其外推为任意全景、变换或真实 PhotoKit 输入均已验收。

文件名、拍摄时间、设备等 metadata 用于上下文、日志与已有历史身份规则，不是静态照片内容候选的强制过滤条件。改名、时间调整、metadata 缺失不能阻止内容匹配；同名本身也不能让新策略跳过不同图片。

候选包括当前 Photos、有效本地待导入/导入中项以及保留的成功历史。向量检索后用持久化的规范化向量计算最终余弦分数，不能直接以近似索引距离作阈值决策。索引输出是相似候选，分数不是“重复概率”。

检索需要覆盖达到判重阈值的候选，不能只拿最近一张决定：必须防止最近的低分辨率版本掩盖另一个已经存在的高分辨率版本。用户于 2026-10-06 选择 SQLite 方案：同一 SQLite 读事务流式遍历全部有效候选，保留原 Float32 `vDSP_dotpr` 精确分数、全部达阈值候选和全局最近 10 条诊断；不保留全量向量堆缓存。SQLite mmap 是可回退的读优化，不是索引正确性的前提。诊断条数不能截断判定候选，本版不引入近似检索。新检索身份为 `sqlite-exact-f32-v1`，必须进入配置、policyVersion 和日志；模型与 fingerprintVersion 不变。旧 `exact-f32-v1` 是历史基线，不能冒充新后端验证。

补充验证后选择系统 SQLite + Accelerate 的单次游标扫描：用一个窄的 C/Swift 桥复用原精确评分和 Swift 同分排序，避免 sqlite-vec L2 粗筛后的二次扫描、排序与复核。此实现不依赖 sqlite-vec、不自制向量数据库或常驻缓存。每条有效候选在评分前校验 BLOB 类型、4096 字节长度、有限分量和原有单位范数容差；不命中的损坏向量也使整次查询失败，不能返回部分跳过证据。候选资格、上下文、版本、尺寸及本地修订仍由现有 SQLite 规则约束。

### 3.2 决策顺序

| 条件 | 动作 |
| --- | --- |
| 已有明确成功历史保护该来源记录 | 保留成功结果，不能因目标消失自动补导 |
| 已提交但结果未知 | 沿用恢复流程，不重新提交 |
| 来源变化、删除或读取故障 | 沿用对应安全规则，不用模型覆盖这些结论 |
| Photos 必需索引不完整、过期或当前上下文无效 | 等待更新；允许扫描准备，禁止新提交 |
| 没有达到当前阈值 0.98 的有效候选 | 导入 |
| 存在满足规则、且分辨率足以覆盖来源的候选 | 自动跳过并持久化证据 |
| 匹配候选都明显低于来源分辨率 | 导入更高分辨率版本 |
| 图片比较成功，但尺寸或其他判定依据不足 | 保守导入，并记录原因 |

分辨率按方向归一化后的原表示像素尺寸比较，绝不使用模型输入尺寸或预览图尺寸。候选长边和短边均不小于来源时，才允许它阻止更高分辨率导入。来源两边均不小于候选且至少一边更大，属于明确的分辨率升级；一大一小、无法可靠取得尺寸等不确认为覆盖。文件字节大小、JPEG 质量猜测不作为分辨率证据。

原始版和编辑版各自配对其自身尺寸。一个大尺寸原图不能自动借用另一个编辑表示的匹配分数证明该编辑图也已高清保存。多个候选中，只要一个真实匹配表示足以覆盖来源即可跳过。

本地尚未成功项作为暂时阻止重复提交的依据时，保留依赖关系，不将它伪装成成功历史；候选消失、失效或不再能提交时，依赖它的跳过项应重新判定。采用稳定的队列顺序避免两个 pending 相互引用导致都不导入。

### 3.3 历史指纹的边界

新成功导入记录保留来源指纹、表示尺寸和版本，Photos 删除后仍能作为历史证据。旧成功记录没有指纹时只沿用已经保存的历史身份保护；允许在正常授权读取范围内补齐仍可读的关联资源，但不为了补齐而扫描停用来源或要求已删除图片重新出现。资源均不可用时，不能承诺跨文件名识别这段旧历史，也不让无法补齐的历史阻断全库就绪。

## 4. Photos 索引是持续同步的本地副本

### 4.1 触发与覆盖

| 触发 | 工作 |
| --- | --- |
| 首次启用 | 枚举现有 Photos 照片，构建所需表示的指纹；完成前不开始导入 |
| 应用启动、恢复运行、图库或授权上下文变化 | 重新核对图库清单及版本，补上离线期间变化 |
| PhotoKit 变化通知 | 合并新增、改变、删除事件；尽快更新受影响资产 |
| 应用运行时每 30 分钟 | 对 Photos 做清单/metadata 对账，补偿漏通知或变化集合不可增量计算的情况 |
| 每轮导入准备及提交前 | 检查对账状态、未处理变化和索引代次；失效则重新判定 |

定时检查与现有扫描节奏合并，不叠加任务、不在休眠恢复后补跑所有过期周期。应用退出期间不引入额外后台守护进程，下次启动补齐。

完整清单对账可以遍历十万条资产的轻量信息，但不意味着重新获取和推理十万张图片。收到变化先关闭可能过期的判重发布权限，再核对变化；完整清单、有效指纹及待处理任务是三个不同事实，不能用一个“全库 dirty”同时代表它们。

### 4.1.1 通知分类与处理范围

| 已获得的证据 | 清单／发布处理 | 已有指纹与工作处理 |
| --- | --- | --- |
| 新增资产 | 加入清单，补齐前阻止新判重决定 | 仅为新增的合格表示计算指纹 |
| 明确的内容或模型输入变化 | 更新受影响资产／表示，旧决定失效 | 仅受影响表示待重算；其他资产的向量、任务和重试事实保留 |
| 已证明仅为不影响模型输入和候选语义的 metadata／系统状态变化 | 更新必要 metadata 和检查点；完成分类核对后恢复发布 | 保留向量，不重新取图或推理 |
| 可靠删除／资格排除 | 相关候选立即停止使用；完成可靠清单关系更新 | 移除相关当前候选和任务，不动其他向量及成功历史 |
| 非增量通知、代次缺口、事件丢失／溢出、范围未知 | 标记需要完整清单核对／复用证据核验，撤销 publication | 保留向量字节和已完成进度；逐项确定可复用与待验证范围，不因该通知直接清空全库向量 |
| 授权不可用、图库上下文不可确认 | 停止新的读取和决定，恢复后核对上下文与连续性 | 保留持久数据；尚未重新证明有效的记录不参与新决定 |

`fullReconcileRequired` 只表达“增量清单不足，需重新对账”，不能隐含“所有照片的内容都已变化”。原始通知序号可前进，单项图像输入修订不因此自动变化。与模型输入有关的方向、色彩解释、所选资源、尺寸、表示等价关系、资格变化不属于可直接忽略的 metadata；通知名称包含 iCloud／缓存或发生在取图期间也不是内容未变的证据。

变化分类按消费方的依赖判断：无需重新生成照片 embedding，不代表可以忽略文件名、视频 metadata 或资格清单更新。既有视频／文件名判重视图和所有提交前检查仍须收到相关变化；本修订只缩小照片指纹的失效范围，不降低这些安全检查。

正常增量必须有明确上下文和连续基线。完整变化集合按有界批次合并处理，先持久化需要处理的资产／任务事实，再确认消费对应变化范围。一个通知包含 129 个已知变化 ID，不应因为批次容量为 128 就将其他十万张照片视作内容变化。如果无法保全完整 ID 集合，则保留“清单需重查”的标记并走完整对账；既有已知内容变化不能在溢出时被遗忘。不能为消除溢出建立无界内存队列或第二套向量库。

### 4.1.2 复用证据与非破坏性对账

每次对账先比较轻量清单和表示信息，只处理新增、变化、删除及无法确认的条目。按 ID 查询没有返回资产不等于已删除；只有可靠删除事件或成功完成的完整清单才能处理缺失项。部分分页、失败或中断不能删除未见项，也不能清空旧向量来表示“这轮没检查完”。

复用要求相同且已确认的图库上下文、表示语义和 fingerprintVersion，并有覆盖待核对区间的内容连续性证据。可用证据包括完整的实时变化集合证明该表示未受影响、有效持久变化历史证明它未变化，或公开 PhotoKit 内容变化详情结合模型输入／候选 metadata 检查证明可复用。明确报告变化但无法区分内容与 metadata 的 ID 只能按受影响资产处理；不能区分 original/current 时可以重算该资产的两种表示。

当前 `revision` 是修改日期和公开资源描述的摘要，不是内容版本或像素哈希。`revisionIsReliable` 不能仅因日期／资源字段齐全，就在历史断档或范围未知时授权复用。相同修改时间、文件名、尺寸、拍摄日期或总数均不能单独证明像素未变；显式内容变化也不能被相同摘要覆盖。对公开 API 能提供何种连续性证据，应有适用条件和测试，无法证明时保持待验证。

“保留向量”不等于“允许使用旧向量”。待验证记录的字节保留在 SQLite，发布屏障保持关闭；证据不足的条目通过有界的重新读取／推理验证。只有确认替换时才更新对应指纹，不在验证开始前批量将全库 `vector` 清为 NULL。若整个连续性区间确实无法证明任何旧表示有效，可能最终需要验证全部表示，但必须记录具体证据缺口，不能只以一次普通变化通知作为全量重算理由。更换图库、fingerprintVersion 变化或索引损坏也须明确范围，不能混用旧数据。

启动、恢复、每 30 分钟的完整检查继续保留。无变化对账在证据充分时须零取图、零推理，对无变化表示／任务零行写入；允许有界的全局检查点写入，不逐行重写 `seen_generation`。临时 seen-key 集合只承担本轮清单完成检查，不另存一份持久全库快照。中断后重新核对清单并复用已确认有效的成果，保留未完成任务、发行身份和有效退避状态。

### 4.1.3 稳定枚举与变化覆盖终点

清单会话身份、原始通知序号和已覆盖变化终点必须分开。一次枚举绑定已确认的图库上下文及稳定的基线清单／fetch result 身份，分页检查该枚举身份有效，不要求整个扫描期间原始通知序号保持不变。不能直接将现有 raw `Photos generation` 当作这三种身份的同义词；适配层须证明所用公开 PhotoKit 枚举视图及变更详情之间的基线关系。

枚举期间持续接收变化。只有覆盖从基线到选定终点的完整、已分类变化集合，才可与基线清单顺序合并：新增补入、可靠删除移除、有关表示及资格更新；已确认不改变清单／输入语义的通知仅推进覆盖终点。部分 delta 不能充当完整终点。基线或关联关系丢失、未知范围尚未核实、授权／上下文不可信时保持不可发布，必要时重开轻量清单会话，仍保留已有指纹。

先提交合并后的清单／表示／任务事实，再对同一上下文、已提交索引版本及最新已覆盖通知终点作最终发布校验。尚有未覆盖通知、待处理详情或未验证表示时不得 ready；最终校验失败只继续补齐或重查清单，不清掉无关向量。此过程不持数据库锁等待 PhotoKit 或其他 I/O，也不声称与外部图库写入有联合事务。

必须通过“每页之间注入已证实不影响输入／成员关系的通知，没有整轮静默窗口”的测试；清单不得因此反复从第一页开始，最终可覆盖一个当前终点并完成短发布校验。与此同时，未覆盖的真实新增、内容变化或未知事件仍应阻止旧终点发布，不能为收敛而忽略它们。

### 4.1.4 清单确认、通知交付与候选基线（10 月 7 日实测修订）

真实只读首批暴露两种现象：一次候选基线接续失败使表示进入待验证；随后已知且输入未变化的通知仍被交付为完整核对。首批 115 次取图涉及 49 个不同表示，最终有 48 个 ready 向量。实际基线失败的具体并发交错尚待受控复现；不得把推测当作已经证实的 PhotoKit 行为。以下约束补足现有连续性设计，不改变判重规则或内容证据要求。

- **清单确认独立于指纹 ready。** 完整清单、持久变化义务和相应覆盖终点已核对落库后，`acknowledgeInventory` 必须解除该终点已经覆盖的通知交付 dirty 状态。无须等待所有指纹计算完毕，随后已知增量应按增量交付。判重 publication／历史 admission 仍由最终 ready 确认独立开放；清除清单标记不能提前允许使用未验证向量或旧决定。
- **确认不得吞掉较新变化。** 只清除已覆盖且详情已完成的状态；代次已经前进、详情未完成、历史或 journal 写入失败、上下文失效时拒绝旧确认。确认与通知入场须保留同一原子有效性约束，不在先检查再解锁后无条件清空 dirty。
- **候选快照不得制造虚假的内容断档。** observer 入场、候选变更排队和快照重建必须有一致的顺序及基线。通知正在排队／分类时，快照不得把候选基线提前标为“已消费该通知”，再令同一通知因基线前移被误判为未知全库变化。应在现有有界队列／锁边界内协调，保留第一时间关闭 admission 的语义；不得用忽略版本不等、删除 fetch-result 身份校验或猜测内容未变修复。
- **保留真实不确定性。** 真正缺失的详情、事件丢失、授权撤销及未知内容仍要求核对／验证；已知编辑或删除不能被中性通知覆盖。回归同时检查文件名候选更新、有效指纹复用和相关晚结果拒绝，不能只断言日志名称。
- **诊断可区分原因。** 基线失败记录通知代次、实际候选基线、期望基线和回退原因；清单确认与最终发布分别记录。需要的字段进入既有诊断通道，禁止加入第二日志系统、原图持久缓存或新个人信息。

新增受控回归：完整核对已确认而指纹仍 pending 后的中性通知；旧确认与较新／未分类通知交错；observer 入场后、详情排队前的并发快照；并发多个有序通知；真实内容改变及权限失效的负向保护。通过可控门闩建立时序，不能以随机 sleep 证明竞态已解决。实际修复、canonical 及只读复验按 [通知恢复修复计划](../plans/2026-10-07-photos-index-notification-recovery.md) 执行。

### 4.2 原始版和当前编辑版

每项表示包含图库上下文、资产 local identifier、表示种类、资源/修订信息、原表示尺寸、指纹版本和状态。原始版表示编辑前图像，当前版表示用户在 Photos 中实际看到的最新编辑结果；不把当前版当作原图。

未编辑资产在能确认两种表示等价时共用一份指纹。编辑后保留有效原始指纹，生成当前版；撤销编辑时合并冗余表示。若无法可靠区分哪部分改变，重新读取受影响表示，不能凭尺寸未变复用。每个匹配结果记录具体命中哪个表示。

Photos 删除资产后移除当前候选；原始版或编辑版内容确认变化后，相应旧表示立即停止用于新决定。晚到结果按具体表示／任务的有效性检查接纳，不能仅因无关通知使全局代次前进就丢弃它。历史成功指纹单独保留，不因当前索引清理而被删除。

### 4.3 一致性与等待

SQLite 是可恢复的指纹事实源和候选查询来源，不再维护第二份全量内存向量视图。资产更新和就绪发布使用代次，只有同一 SQLite 快照中的清单、表示、任务全部完成，并按 §4.1.3 证明基线至终点的变化覆盖、通过 PhotoKit 当前上下文／终点校验的令牌才能用于新的判定。发布仅传递令牌与计数，不加载整库向量。崩溃、部分写入和索引损坏后从已提交数据恢复，不能清空用户同步历史。

全局发布代次与单项任务发行代次分开：更新一个资产不重写无关任务。任务完成须核对持久任务身份、发行代次、表示修订、尺寸、等价关系、指纹版本、上下文及墓碑；已替换/撤销任务的晚结果不能复活旧表示。无关变化不单凭全局代次前进而废弃仍有效的任务结果。

首次完成后也不盲目信任旧代次：已经观察到新增或内容变化，就暂停新提交，补齐后恢复。未验证输入不能被悄悄排除；但用户于 10 月 8 日明确批准将单项 PhotoKit 取图异常记录并跳过，具体范围和恢复规则见 §4.3.1。已正确分类、持久化的读取错误不再阻止健康表示构成可用索引；它不是成功指纹，也不证明该图片损坏。确认不属于高级照片范围的资产仍按确定性类型规则排除并计数。

沿用 `PhotosCandidateSnapshot` 的有效性与提交检查模式，增加索引代次和本地候选修订；数据库事务内校验本地依赖与跳过证据。不得持数据库锁等待 Photos、下载或模型。每次异步等待后重新核对暂停、来源状态、文件 stamp、图库上下文及与当前操作有关的表示／发布有效性；提交仍必须检查最新发布令牌。

公开 PhotoKit 查询与提交不是跨进程事务；其他应用恰好在最后检查后导入的竞态无法彻底消除。本版保证处理已观察到的变化和重新校验，不宣称跨应用全局恰好一次判重。自身成功导入通过本地记录立即参与下一次比较，不等待 Photos 通知才生效。

### 4.3.1 单项 PhotoKit 读取错误隔离（10 月 8 日用户批准）

实现与自动验收已在 `a190279` 完成；[验收记录](../../release/2026-10-08-photos-read-error-isolation-validation.md)单列真实 Photos 续测、平台及分发的剩余边界。已知网络／授权／图库／取消错误即使嵌套在普通 NSError 内，也保留保护语义；无法完整检查的错误链不获得读取错误豁免。

用户指令：“接受与 photokit 交互可能会出错这一情况，catch 对应的 exception，记录日志，不影响其他图片建指纹。”本规则覆盖单个 original/current 表示，优先保留同一资产的其他健康表示；不是按资产整项删除，更不修改 Photos 或来源文件。

10 月 9 日补充：错误的隔离与恢复取决于性质、任务有效性和实际资源状态，不要求只出现一条错误。只读测试也遵循这一原则；批次暂停用于核对现场，不得把批内错误数量变成永久恢复门槛。超时仍须等待实际请求结束后再按退避重试，全局故障恢复前的保护和最终发布要求不变。

- 在读取阶段明确识别 PhotoKit 最终回调错误和单张返回图像无效／超限；包括实际遇到的 `NSCocoaErrorDomain/-1`，无需把其底层原因猜测为坏图。错误来源必须由类型和阶段确定，不能从历史 `last_error` 文本反推，也不能在同时包含取图、推理和落库的通用 catch 中全部放行。已识别的 iCloud／网络等待、授权或图库不可用、上下文／内容变化、取消／超时／物理占用、模型和数据库错误仍按既有阻断或等待处理。
- 沿用表示状态 `failed`，在其 `fingerprint_task` 增加持久化 `failure_kind='photos_read'`，保留错误、次数和重试期限。其他失败为 NULL。只有仍匹配当前上下文、内容修订、指纹版本及任务发行身份的这类记录可作为已处理的读取缺口；旧向量不得参与匹配。清单完整和变化覆盖仍须成立，pending、未分类失败、孤立／错配任务仍阻止发布。
- 健康表示继续取图、推理和落库。全部项均已成为有效向量或上述明确读取缺口后，允许发布可用索引；向量查询只取 `ready` 行。日志／进度分别报告成功指纹、读取错误和其他等待，不能把错误算进 ready，也不能用资产级类型排除数混淆表示级错误。用户接受这些缺口可能漏掉仅与不可读表示重复的来源照片；没有命中只表示当前可用候选中没有命中。
- 保留既有到期重试和退避。中性变化不清除错误分类或重试期限；相关内容替换、未知连续性失效或版本变化须清除旧分类，重新验证。相同读取错误重试失败不扰动健康候选；重试成功增加候选，或错误转为不可容忍故障时，须原子推进索引代次并撤销旧 publication，再经原发布校验开放。旧准备结果不能在变化后的候选集合上继续提交。
- 仅扩展已有诊断和进度字段，记录错误阶段、系统详情、表示身份及重试信息。保留原生 UI 和“就绪后隐藏图库分析”的设计，不增加人工判图、错误忽略按钮、原片下载兜底、新后台服务或任意错误率阈值。既有系统状态和资格判定不能因为用户接受单项错误而放松。

实施与回归见 [PhotoKit 单项读取错误隔离计划](../plans/2026-10-08-photokit-read-error-isolation.md)。真实验证报告须区分清单覆盖、可用向量和读取缺口，不将可用索引称为每张照片均成功取图。

### 4.4 初建期间持续变化与恢复

初始化期间使用同一可恢复任务队列吸收新增和编辑，已完成的无关向量不因事件到来归零。全局 publication、清单核对状态与单项任务发行身份分离；撤销 publication 不得连带删除向量、重置所有任务或延后无关任务的退避期限。

单项读取／推理完成时，按该资产／表示、任务身份、内容证据和上下文判定是否可接纳。无关资产变化或已证明无输入变化的通知不取消它；相关编辑、删除、资格变化、任务替换必须拒绝其晚结果。范围未知期间允许实际在途操作正常结束并释放资源；无法证明输入仍有效的结果不能标为 ready，仅该未确认任务保持待验证／重试，不连带清掉其他已完成向量。

对账期间到来的事件必须继续保留并顺序归并到核对终点；有界轻量核对必要时可重启，但指纹建设不能同步从零开始。重复投递同一已覆盖事件应幂等，不能仅凭事件“理由相同”把两个未知变化当成同一事件。已知变化按最后有效状态合并，未完成的事件详情／未知区间仍阻止发布。

历史覆盖核对中的未决通知或进程内边界变化属于暂时等待，不能直接等同于持久历史缺失并清空全部可用资格。此时沿用 `libraryChanged` 拒绝当前核对，保持 publication 关闭，等待详情完成并以新上界重试；不能提前假定通知不影响输入，也不能承认旧上界已经覆盖。保留向量、已分类读取缺口和退避事实；后续详情若证明相关内容改变或真正未知，仍按原规则失效。历史不可读取／不完整、上下文不连续、持久义务无法保存等真实连续性缺口继续触发保守失效。

收敛要求：在有限真实内容变化和持续、可确认不影响输入的通知下，初始化最终能够完成，重复通知不会反复重新获取未变化图片。持续无法分类的变化可以使新判重决定继续等待，但应展示原因、保留成果和有界退避，不忙循环、不自动放宽完整性要求，也不承诺任何外部变化速度下都能立即 ready。

这些是索引内部的有效性状态，不增加来源文件的四种用户状态，也不引入人工判重操作。实现优先复用既有 SQLite 表、任务和 publication 分离接口；需要新增持久字段时须在实施计划中给出必要性、事务迁移及崩溃恢复契约，不能以此重构整个存储层。

## 5. 图像读取、iCloud 与资源预算

通过公开 PhotoKit 请求明确版本的图像表示；只有最终、满足版本与质量要求的结果才能生成正式指纹。降质预览、取消、错误或空结果均不能标记就绪。原表示尺寸必须来自对应资源的可信信息，不能用缩略图尺寸代替。

允许网络访问使 iCloud-only 图像按需获取，不更改 Photos 的存储设置，不要求用户永久保留所有原片。目标请求尺寸不等于网络传输字节上限，Photos 的缓存保留由系统决定；UI 和文档应说明初次索引可能下载数据且受网络影响。应用不在自己的数据目录持久保存原片或预览副本，仅保留指纹及必要信息。

图片读取/解码、iCloud 请求、推理都有固定的并发和在途内存上限；推理初始采用串行、批次 1，避免推理数量随图库增大。暂停停止新任务，已返回结果可安全落库，取消与超时不能绕过仍占用的实际资源槽位。网络或单资产失败使用有界退避，不忙循环；恢复时只重做未完成或失效项。

Photos 初始化和增量更新与来源准备共用受控资源预算，不能让十万张初始索引产生十万个同时存在的任务或解码对象。UI 只消费节流后的聚合进度。

## 6. 存储、迁移与模块边界

沿用现有 SQLite 与串行写入路径，事务化升级已支持的旧 schema 至 v7，并同步核对代码迁移和 `Schema.sql`。v5 的资产排除事实继续保留；v6 增加同库 `photos_content_change` 轻量义务记录和任务的不可变 `issuance_revision`。v7 仅在任务增加可空 `failure_kind`（NULL 或 `photos_read`），历史错误默认为 NULL，不凭旧错误文本授权跳过。迁移保留已有向量、任务退避、成功历史和 unknown 提交，撤销旧发布；各旧版本迁移失败须整体回滚。升级后须重新证明清单及历史覆盖，不因字段齐全就将旧数据标为可用。不建立第二套向量库或成功历史。

- `Photos/`：资产清单、变化通知和指定表示读取，不承担判重策略。
- 指纹组件：统一预处理、Core ML 生命周期和版本检查；模型产物随 App 分发。
- 检索组件：增删改与候选检索，支持由 SQLite 重建以及精确检索基准。
- `Matching/`：输入有效候选、分数、尺寸和版本，输出动作与原因，不直接执行 I/O。
- `Storage/`：迁移、原子发布、历史保护和证据一致性。
- `SyncEngine` / `SyncRuntime`：协调索引维护、已有扫描/重试与串行提交。
- `AppModel` / 日志：显示索引进度与问题，提供有界诊断信息。

模型或预处理版本不一致时禁止混用向量/阈值，重新构建对应指纹；旧已提交结果和成功历史不得因此重新导入。仅修改阈值时更新 policyVersion，保留相同 fingerprintVersion 的指纹与索引数据，不重新下载或推理全库；旧策略的决定不能直接复用。向量索引格式更新只重建派生结构。未知更高 schema 拒绝打开，禁止删库重置或静默降级。

旧策略的疑似重复项（包括 0.1 及以后调整阈值前的高级判重）以可恢复的批处理重新进入判定：只处理启用来源、仅因疑似重复跳过、没有成功证据且没有未知提交、决定策略缺失或不同于目标策略的照片。检查来源仍存在且未触发 `sourceChanged`，再重新比较。视频和其他跳过原因不变。进度按目标 policyVersion 保存；同版本重启幂等，版本变化重新遍历符合条件的项目。来源重新启用/重新添加后也须补扫此前游标已经越过的合格旧项，不能依赖普通扫描的 stamp 变化触发；已按当前策略判断的项目不重复重开。迁移中断可恢复，不一次性清空所有 skipped，也不把重判计为新成功。

- 产品继续只新增；验收宿主的收尾能力仅能回收本次确证新增、基线中不存在的精确资产 ID，不触碰既有照片/相簿/最近删除项，也不回滚期间正常的用户/iCloud 变化。测试用编辑、撤销仅限这些新增资产。
- 原状核验分别报告既有资产/来源/生产运行状态、活动图库新增清理、最近删除收尾及不可逆的缓存/同步记录。不能把活动图库数量恢复当成无残留；公开 API 不保证系统缓存和 iCloud 历史逐字节还原，未完成清理须保留待处理状态。

具体新增上限、分阶段门槛、精确 ID 台账与停止条件由当前真实图库计划固定；不改 0.98、产品算法、发布范围或已接受的平台缺口。

2026-10-07 用户另指定 MobileBackup 真实待同步目录，要求实际 Photos 指纹库与全目录只读内容评估、metadata＋子代理独立发现重复和双向抽查。按真实图库计划 V3-MB 执行：候选只含 Photos 表示，源向量放独立审计 sidecar，避免本地待导入项/成功历史掩盖当前图库内容漏检；复用原产品解码、模型与 SQLite 精确评分，不称为完整导入准入。先冻结独立盲审标签再揭示分数；随机与边界样本分开，未知不当阴性，不重调阈值、不公开私人图片。此项不执行 Photos 写入或生产数据库操作。

## 8. 性能验收

在 M2 Pro 上记录冷启动、热运行、P50/P95/P99、峰值 RSS、持久存储和 CPU/GPU 占用。分开测图像读取/下载、预处理、推理、检索、SQLite 与总等待，不能只报模型耗时。

基准覆盖十万资产的全未编辑、一半编辑、全部编辑情形（最坏约二十万表示），以及单张/批量新增、编辑、删除、退出续建、休眠恢复和无变化的 30 分钟检查。1024 维 Float32 原始向量每十万表示约 409.6 MB，二十万约 819.2 MB；尚未包含索引、数据库页、历史、本地队列、模型或解码内存，不能用模型大小代替 App 内存。

验收必须证明：无变化对账不调用模型、不下载图片；单项变化只使有关表示重算；在途任务、解码内存和推理并发有固定上限；索引可分块恢复；UI 在索引过程中仍可暂停。复用当前精确检索实现与合成规模基线；集成后的测量明确标出输入规模和真实/合成来源，不为本次阈值选择重新启动算法选型。

当前集成契约为 `background-preparation-v2`：M2 Pro 上缓存命中与新来源的完整判重准备均要求 P95 ≤2 秒，Photos 单项变化到有效就绪保留既有 2 秒上限，峰值 RSS ≤4 GiB。纯查询的 P50/P95/P99 单独记录，不再以 250 ms 作为跨规模阻断门槛。这是当前后台工作单元的工程预算，不是 UI 响应或包含 PhotoKit/iCloud 的完整导入 SLA；旧数值及其不同精度/设备/口径的依据见[指标复核](../../research/advanced-dedup/2026-10-06-performance-budget-reassessment.md)。固定配置的并发/内存上限必须通过产品测试，实测超标须修复或报告后再判定发行。独立准确率研究不再阻挡进入集成；十万真实资产与真实 iCloud 如未执行须列为缺口，不用合成数据替代通过。真实 iCloud 耗时、流量及缓存影响单独记录，不从本地 JPEG 数据外推。

2026-10-06 补充资源目标：常驻应用以低闲置占用为优先，分别报告 RSS、私有 physical footprint、可回收文件映射及查询后闲置/再次查询的变化。查询不得产生向量表、临时排序文件或其他持久写入；导入和变化维护的必要事务、WAL/检查点、决策日志另行测量，不能从查询零写入推导整个应用零写入。无变化对账应零表示/任务行写入，一项变化的写入量应与受影响表示数相关，不随全库数量增长。逻辑读取、进程记账读取与物理 SSD/NAND 写入必须区分。

最后的单遍原型在 100k/300k 合成向量上热查询 P95 为约 125/478 ms，查询部分 footprint 约 6 MiB；最大档仍超 250 ms。该事实支持实施 SQLite 以降低驻留内存，不构成性能验收通过。后续以实际完整产品路径重测，保留失败项，不调整阈值、删数据或放宽门槛来得到通过。

2026-10-06 的最终受控产品组件测量（`1714857`）已补齐：100k/150k/200k Photos 表示及 200k+100k 成功历史的纯查询 P95 为 168/253/339/612 ms，热准备 P95 为 233/344/455/732 ms；单张变更到有效就绪的各类 P95 均不超过 358 ms，峰值 RSS 均低于 1.80 GiB。后三档按当时 250 ms 目标未通过，61 MP 16-bit PNG 单次准备也出现 2.24–2.56 秒。四档纯查询零写入、无变化核对零表示/任务/排除行写入；最大档 60 秒闲置 footprint 约 30.49 MiB、RSS 约 1.30 GiB。这些是合成图库的受控进程值，不是实际 Photos/App 闲置或 SSD 磨损证明；详细口径与未完成边界见 [验收记录](../../release/0.2.0-advanced-dedup-validation.md)。

本日指标复核后的新验证绑定 `477284b`，四档均按 `background-preparation-v2` 通过：缓存准备 P95 为 225/341/454/736 ms，新来源准备为 300/431/555/845 ms；峰值 RSS 最高 1.86 GiB。最大档 60 秒闲置 footprint 约 23.99 MiB、RSS 约 1.49 GiB；61 MP 16-bit PNG 两个单次观察为 2.22/2.46 秒，仍不代表所有大图满足预算。新验收只改变测量契约及校验代码，产品路径未加速，旧 FAIL 未改写；统计与真实系统边界保持上述限制。

## 9. 日志与可解释证据

扩展已有轮转 JSONL（当前 10 × 10 MiB）和 SQLite 判定证据，不新增日志服务。每次新的导入/跳过决定记录：

- 来源记录 ID、文件 stamp、Photos 资产/本地候选 ID 与表示种类、时间、判定事件 ID；
- 模型/预处理/策略配置版本、用户决策 ID（acceptanceID）、实际阈值、图库与索引代次、就绪覆盖数；
- 最终动作和原因，来源与命中表示的原始尺寸；
- 全部候选来源合并后的最近 10 条诊断候选精确分数及 `score - threshold`，包含阈值以下近邻；独立保留最多 1 个决定候选，不因诊断截断丢掉覆盖证据；分数保留可往返的 Double 精度，无候选记空值及原因，不造 0 分；
- 读取、下载等待、推理、查询等分段耗时，失败阶段与系统错误详情。

导入也要记，尤其是门限附近的未命中和分辨率升级；不能仅记录成功跳过。重复扫描中的同一文件、相同 stamp、相同策略与有效证据不重复输出全套详情；策略变化、候选失效或重新判定形成新事件。批次索引日志记录触发原因、新增/更新/删除/失败/等待数量和耗时。此次修订还须区分原始通知、分类证据、完整清单回退理由、内容失效范围及 publication 撤销理由；记录保留、待验证、重算的表示数和实际取图／推理次数、重算原因及收敛进度。无法解释的全量回退不能只留下一个 `libraryChanged` 字符串；这些诊断仍受既有脱敏、轮转和不记录图片／向量的限制。

SQLite 保留当前决定所需的关键跳过证据与成功关系，不受 JSONL 轮转影响；普通诊断只保留有界候选数量，旧的非关键诊断随轮转淘汰，不积累所有 pair。日志不保存图片、完整 embedding 或图像 metadata 全量转储，不自动上传。日志写入故障沿用警告语义；数据库关键证据写入失败则不能提交一个无法持久化的跳过决定。

生产日志用于观察分数分布、边界样本、规则触发和版本回归，不能凭分数本身证明判对，也不自动根据线上分布改变阈值。更新阈值按第 7 节进行显式决策、固定回归和版本升级；本轮不要求恢复已停止的独立校准。只有阈值改变时不重算指纹，但必须重新判断符合条件的旧 skip；成功历史和未知提交继续受保护。

## 10. 用户体验
