# PhotosYNC 运行时状态与恢复契约

本文是 PhotosYNC v1 在“扫描、恢复、计数和用户提示”方面的实现契约。产品范围仍以
`outputs/2026-09-13-photo-sync-v1-design.md` 为准；本文补充其没有详细规定的运行时边界。
实现、测试和后续重构发生冲突时，先遵守本文和产品设计，再修改本文并记录迁移理由。

2026-10-21 的 Live Photo 行为以[完整 Live Photo 设计](../superpowers/specs/2026-10-21-native-live-photo-completion-design.md)为补充；下文历史 schema v3 说明不代表当前数据库版本。

## Live Photo 补充契约（2026-10-21）

- schema v11 事务迁移并保留成功历史。源文件仍只有四种状态；组的创建、验证和清理单独持久化，两份资源保存计两个文件。复用已有目标不伪造成功导入。
- 每个文件夹完成直属枚举和本轮有界身份识别后放行；历史 pending/retry、跨目录配对和实际提交前守卫都复核该条件。失败文件隔离，健康兄弟目录可继续。
- 首次历史识别使用固定任务键，分批断点续跑；全部枚举并完成本轮尝试后持久化完成。待核实项按项重试，重启和常规升级不重跑全库。初次分析及旧未完成项重试允许按需获取 iCloud 原文件；确定失败不计入已处理分子。
- 仅有 Photos 的历史工作不依赖启用来源，仍受暂停与图库授权约束。来源身份观察先于普通判重；缺半先保存，后到按精确身份及原资源版本补齐。潜在完整目标未核实前不新建重复目标。
- 一个实际 PhotoKit 提交槽位覆盖普通导入、成对创建及定向清理。组事务预留成员，普通 drain/retry/recovery 排除这些成员；创建或删除未知时，重启也先恢复全局阻断。缺少查询结果或匹配删除事件不能证明提交成功或失败。
- 补齐先记成功，再验证原资源、原生对象及音轨；精确旧项的原资源和其余受保护信息已保留后清理。按用户确认，标题不作保护：未知、不同或单独的标题变化均不阻止清理，可能丢失旧标题。资源版本变化、编辑、额外资源、共享相簿或其他受保护信息未知仍保留旧项。
- 公共 SDK 无稳定物理图库 ID。历史上下文恢复必须取得已知资产的正向连续性证据；权限/图库不明时等待，不把 session、epoch 或 opaque token 当作物理图库身份，也不通过重置一次性标记绕过。
- Live Photo 临时原资源共用 512 MiB 预算和 128 MiB 磁盘保留；逻辑超时不释放仍在物理读取、解析或验证的槽位与资源所有权。来源不暂存、不改写、不转码。
- 原资源读取使用600秒请求期限、610秒逻辑期限；取消只发送一次，实际 terminal 前保留物理槽位、临时文件及预算。临时失败逐项60秒重试；确定无法解析、单资源或本组固定工作集超限暂停该版本自动重试，资源变化或“立即扫描”可重新尝试。其他任务暂占预算走5/5/15/15/60秒正常 deferred。
- runtime 独立持有一个 Live Photo worker，每片最多 16 轮，每轮最多一个历史资产和一个组操作；有实际推进时让出执行权后继续下一片，等待或无进展时退出（2026-10-23 修订）。两类 catalog 仍由一个串行入口枚举；不放宽创建、验证和清理守卫。身份观察允许覆盖完整的无关资产变化，目标变化、删除、权限变化或未知覆盖仍拒绝。
- 进度复用同一份菜单、设置和 hover 投影；下载和保存都是内部步骤。受保护信息导致保留已验证旧单项是正常结果；失败或未知删除仍单独保留。系统原文只进入诊断详情、提示和日志。

## 任务推进与进度补充（2026-10-22）

- 保留六个标题：正在准备、正在同步、等待恢复、已暂停、需要处理、同步完成。已到期且准入允许的排队工作与执行中的工作同属活动任务；未来重试、容量占用和未核实依赖仍是等待，未知写入保持阻断。
- 视觉索引、Live Photo 各保留一行说明和自己的 5pt 纯色进度条，顺序固定；总量未知使用活动短段，不编造百分比。等待和暂停保留数量及 hover 锚点、停止动画。下载和保存仍只作为内部步骤；任务 hover 说明计数口径、云端流量、续跑及旧单项影响。
- 原件完成时若通知仍在分类，在现有 producer 队列中等待一次 FIFO 标记（最多 5 秒），随后重新验证目标资源。分类暂未完成只延后当前任务，不触发整个 Live Photo 队列的 60 秒冷却；目标真变只刷新该目标。资源版本、权限、未知覆盖和物理所有权守卫不放宽。
- 视觉解码确定超限采用 schema v11 的 `photos_read` + `Date.distantFuture` 保留编码，停止同修订自动重读；明确“立即扫描”或精确输入变化才重开。健康表示可继续发布，保留项仍独立计入“需处理”，不混成普通临时失败或完成。
- 状态查询只用存储事实和轻量队列摘要；实际判重和写入仍复核 PhotoKit。无到期工作跳过空消费，补齐身份发现按变更分批完成，不因 UI 轮询重复扫描。
- 日志按匿名 handle 记录读取准入、原资源读取、通知分类、元数据、版本验证、观察入库和补齐阶段；30 秒有工作才汇总。资源字节数不等同于实际网络下载量。

## 1. 四层状态，不能混用

PhotosYNC 同时维护四层状态：

1. **文件状态**：数据库中只有 `pending`、`importing`、`imported`、`skipped` 四种状态。
   重试次数、`next_retry_at`、`last_error`、attempt 和跳过原因都是字段，不是第五种状态。
2. **来源问题**：说明目录、单文件或提交是否有未解决问题。来源问题使用
   `SourceIssueKind` 分类：`sourceAvailability`、`file`、`submission`。
3. **本轮扫描状态**：`ScanProgress` 的 `notStarted`、`running`、`completed`、`interrupted`，
   以及本轮的 `checkedCandidates`、`newlyImported`、`failedFiles`、`deferred`。
4. **全局阻断/警告**：Photos 授权、图库上下文、数据库、提交结果不确定等需要人处理的阻断，
   与日志写入失败、通知未授权等非阻断警告分开保存。

不能用“有一个 waitingSources 项”推断整个来源不可用，也不能用某一轮的 `failed` 推断
数据库中的文件状态。

## 2. 来源问题分类和调度

### 2.1 来源不可用

目录不存在、卷未挂载、权限拒绝、网络连接中断、来源配置失效等属于
`sourceAvailability`。这类问题：

- 来源行显示可行动的人话，系统原文只写日志、`scan_run.last_error` 和 tooltip；
- 进入来源退避：第 1/2/3/4 次为 5/15/30/60 秒，第 5 次起为 300 秒；
- 该来源从普通扫描集合暂时移出，只由到期恢复探测重新加入；
- 成功扫描后清除来源退避和来源问题，并发送一次恢复通知；
- 相同问题重复出现时不重复写相同的失败日志或通知，但每轮仍保留批次证据。

### 2.1.1 配置根目录的读取与提交准入（2026-10-16 补充）

根目录与部分子目录共用目录问题槽位，但只有配置根目录整体不可访问才关闭该来源的新读取和提交准入。
冷启动尚无根可访问证据时，已有 pending 和到期文件重试也必须等待根目录实际枚举成功。
根枚举失败后，后续 pending 不逐条读取、不新增文件重试；仅沿用来源恢复退避，定时到期本身不开放准入。
图库索引就绪或历史工作重新入队的自动扫描不能绕过已登记的根失联恢复期限；子目录问题不额外过滤这些自动触发，显式手动扫描保留立即探测语义。

子项属性、文件读取或子目录枚举失败时，通过原有有界 reader 复核根目录。根也失败则记录根目录的真实系统错误，
结束该来源当前遍历/队列工作；根可用则保留原独立文件/子目录错误并继续健康兄弟项。复核 busy/超时仅 deferred，
关闭后续提交读取直到下一次实际根枚举成功，不可据此发布根失联。已确认根失联时，该来源不再额外走 deferred 曲线。

根失联期间，既有紧凑来源行与 hover 只投影根目录诊断；独立文件及提交问题保留在内存和持久化证据中，
恢复后按原有规则重新显示、核对或解除。根恢复准入只依据实际根枚举成功；若该读取发出后发生较新的准入关闭，旧成功续体不能重开准入。停用/移除同样使旧根读取失效。
目录问题槽位的完整遍历恢复门槛仍保留。
只阻断该来源，其他来源与图库索引继续。已经发出的 Photos 请求、晚回调、unknown 和检查点证据仍按原提交生命周期结算，
不能将关闭新准入解释为物理请求已取消，也不删除 pending、成功历史或自动停用来源配置。

### 2.2 单文件或提交问题

支持格式文件不可读、元数据解析失败、提交前 stamp 失败、Photos 明确拒绝某次导入，
分别属于 `file` 或 `submission`。这类问题不能把健康目录送入来源退避：

- 其他文件继续扫描；
- 来源仍按正常周期扫描；
- 文件级明确未提交失败才写 `last_error`、增加 `retry_count`，并使用文件退避 5/15/30/60 秒；
- 单文件错误可在来源行展示，但不能计入“来源等待恢复”数量；
- `failedFiles` 只统计本轮真实文件读取失败，不统计目录失效或提交结果不确定。

### 2.3 读取竞争和逻辑超时

`ReadExecutorError.sourceBusy`、`timedOut`、`resourceExhausted` 表示有界读取排队或等待结束，
不是文件损坏或来源失效。它们必须：

- 不增加 `failed` 或 `failedFiles`；
- 不建立 `waitingSources` 问题、不发来源通知、不写失败日志；
- 不改变文件的 `last_error`、`retry_count`、`next_retry_at`，也不把文件变为 `retryPending`；
- 只把当前内存扫描标记为 `deferred`，菜单显示“稍后继续”；
- 使用独立延迟曲线：第 1/2/3/4 次为 5/5/15/15 秒，之后 60 秒封顶。

来源故障 deadline 和读取 deferred deadline 必须独立保存；清除其中一条曲线不能清除另一条。

### 2.4 来源文件正常删除（2026-09-23 补充）

只有来源根目录和全部子目录已完整枚举，才能认为未再观察到的 `pending` 文件已从来源删除。
目录项属性读取失败时无法确定它是否为目录，因此也不能对其后代作删除推断；其他文件的媒体元数据失败
不妨碍已完整的目录枚举。确认删除后，仅在该行仍为 `pending` 且从未提交 Photos 或有明确未提交证据时，
事务性移除待导入记录及其判重证据。`importing`、未确认提交、`imported` 及其成功历史一律保留。
引用被移除待导入项而跳过的文件必须重新进入判重流程；新的跳过写入前须在同一事务核对本地候选仍有效。
队列游标不得依赖可能被移除的记录继续存在，晚到的读取/重试也不能把正常删除报成数据库故障。
删除事件不计 `failed`、`failedFiles` 或 `skipped`，不发“来源恢复”通知；旧的文件扫描及提交问题一起清除。
同路径以后再出现时按新文件重新发现，仍受成功历史与正常判重规则约束。

### 2.5 当前来源诊断明细（2026-10-15 补充）

`EngineSnapshot.sourceIssueDetails` 是现有内存问题的只读投影：每项保留稳定身份、原问题类别、
失败处完整路径、人话摘要、已知读取步骤及完整系统错误链。每来源按路径、身份排序，空集合移除 key。
文件扫描身份仍为 `scan:file:<relativePath>`，提交身份仍为 `file:<record UUID>`；同一路径两类问题
分别保留。重复失败只更新该身份，不按错误文案累加。`sourceFileIssueCounts` 仍只数扫描文件问题。

目录故障仍共用原 `scan:directory` 恢复槽位，槽位内按完整目录路径保留多个诊断成员。
某目录 entries 成功只移除自身诊断及日志签名，不重置兄弟目录；primary 从剩余成员按路径、身份选取，
摘要与详情必须来自同一成员。成员全空但遍历尚未完成时，保留 sourceAvailability 槽位，使用中性摘要
“目录扫描尚未完成，稍后继续”，不制造诊断项。只有原完整目录遍历门槛成立才移除槽位；不能据诊断项数清除来源
退避或提前发恢复通知。纯 deferred 不创建该标记。停用、移除及既有单项恢复路径同步清理明细。

目录项属性失败尚不能证明它是文件或目录：阶段为“读取目录项属性”，主体为“目录项”，
保留原 NSError 及 underlying 链，并保持遍历不完整、禁止后代删除推断。以后明确读到同一目录项
是目录或非候选项时，只清该项旧扫描诊断。对于从未成功解析、没有 file_record 的旧扫描问题，
本轮仅记录未见的旧诊断键；完整且非 deferred、未暂停的遍历才能按明确缺失清除它们，不发恢复通知，
不修改文件状态、成功历史、未知提交或来源退避。未完整遍历、属性失败、deferred 或旧续体不构成缺失证据。

文件错误只按明确 Cocoa/POSIX 原因区分路径、权限或网络；类别仍为 file。未知视频元数据错误显示
“视频元数据读取失败，具体原因尚无法确定。”，其他未知文件错误显示“文件暂时无法读取，具体原因尚无法确定。”，
不从扩展名或 -11800/-12979 猜测损坏或解码支持。四个必需视频 load 分别记录“读取时长”、
“读取创建日期”、“读取公共元数据”、“读取拍摄时间文本”；可选尺寸读取语义不变。
错误链保留每层 domain/code/description 并防环，不截断或 dump 无关 userInfo；日志保留同样的已知步骤
及系统诊断。必需读取失败仍抛错，健康兄弟继续。以上不新增持久化状态或变更判重、提交、调度决策。

### 2.6 目录状态与文件问题展示（2026-10-19 修订）

来源行和诊断详情使用相同的两层投影：目录/连接诊断属于可用性状态，不能计入“X 项问题”。
配置根目录失联时，主菜单和设置来源行直接显示“来源目录不可用，等待恢复”，并使用警示图标；
仅部分子目录失败时显示“部分子目录不可用”。只有文件读取/解析或文件导入/提交诊断参与问题数量，
同一路径不同诊断身份仍分别保留。目录故障和文件问题并存时两者分别展示，不以问题数量覆盖目录状态。
没有剩余目录诊断、但完整遍历尚未完成时，扫描阶段显示“正在扫描目录”；暂停、延后或空闲时显示
“目录扫描尚未完成，稍后继续”。提交或其他来源的工作不能据此显示为当前目录正在扫描。

此展示口径复用既有根目录检查、文件检查和恢复准入，不新增持久化状态或改变重试调度。
根目录失联期间仍只显示根诊断，独立文件证据保留，恢复后按原规则重新显示。

## 3. `scan_run` 和日志语义

读取 deferred 不是失败。为保持 schema v3 不增加状态字段，deferred 扫描可落一条
`complete = 1, failed = 0, last_error = NULL` 的 `scan_run`，同时在内存
`ScanProgress.deferred = true`，并写扫描事件 `result = deferred`。不得写 `result = failed`。

真正的目录或文件错误才允许把扫描标为失败、增加失败计数并写 `last_error`。提交前 stamp
读取发生 deferred 时，不调用 `recordRetry`；文件行保持原样，后续由来源 deferred 调度再次尝试。

日志按“状态变化”去重：同一来源、阶段、路径和错误签名不重复写失败行；不同子目录或文件
必须使用不同的 dedupe key。每轮 `scan_run` 仍然保留，不得用日志去重代替批次审计。

## 4. 计数和菜单文案

持久统计与本轮事件分两行：

- 持久统计：启用且未移除来源的 `imported`、`skipped`、无错误 `pending`、明确未提交的
  `retryPending`、`importing`；这些数字来自 SQLite 汇总；
- 本轮事件：检查候选数、新增导入数、本轮文件读取失败数、不可用来源数。

停用或移除来源的成功历史不重新计入活动统计，但通过 `retainedImported` 附注告知用户历史仍在。
不支持的 RAW/XMP 等非候选文件不进入候选数，也不写成 skipped。

首行文案必须是人话，不能直接展示 Foundation/POSIX 原文：

- 来源目录不可用、卷未挂载、无权限、网络中断、文件不可读、导入未确认、检查点失败、
  数据库停止、图库不可用和 Photos 未授权各有明确摘要；
- 原始错误仍保存在日志、`scan_run.last_error` 或 tooltip 中；
- 日志写入失败是 warning，不得改变全局错误图标或阻止同步；
- 通知使用 `SourceIssue.summary` / blocking summary，不发送原始系统错误。

## 5. 全局状态优先级

用户只看到六个整体状态，来源集合先与启用来源 ID 取交集：

| 标题 | 条件 |
| --- | --- |
| 正在准备 | 启动状态尚未读到，或视觉索引／历史 Live Photo 分析实际推进 |
| 正在同步 | 来源扫描、判重、提交，或 Live Photo 补齐、验证、清理实际推进 |
| 等待恢复 | 剩余任务在等自动恢复、资源或重试；未知 Photos 提交也归此状态 |
| 已暂停 | 用户暂停；在途结果继续按原生命周期结算 |
| 需要处理 | 全局授权／存储阻断、工作结束后缺少来源，或只剩无法自动处理的项目 |
| 同步完成 | 本轮结束，无未处理、重试、验证或未确认结果 |

优先级：全局需人处理阻断 → 用户暂停 → Photos 未知提交安全等待 → 实际同步 → 实际准备 → 局部需处理 → 自动等待 → 完成。来源失联不能隐藏其他正在推进的任务，失联原因仍单列。未知提交原因显示“等待‘照片’确认结果，新的保存已暂停”，公共写入阻断不变；检查点持久化失败仍是全局需处理问题。

生产者发布 `sourceActivities`、`indexActivity` 和 `livePhotoActivities`；`activeWork`、持久化的首次完成标记和旧错误文本都不能替代实际活动。没有启用来源但仍有 Photos-only 历史工作时继续处理，结束后提示添加或启用来源。

前两种状态显示进度，小字仅用“正在建立视觉索引”“正在配对 Live Photo”。两类任务分别计数，不与来源文件合成总百分比；视觉用“已分析 X / Y 张”，历史分析用“已处理 X / Y 项”。总量未知省略分母，失败不计入分子，组验证／清理用不确定进度。hover 解释用途、必要的 iCloud 流量和系统缓存、保存结果与重启续跑；支持悬停、点击固定、键盘及 Escape。原因和用户动作常显。

菜单、设置使用同一份投影和丝带图标；准备复用运行中标记。只有整体为等待且启用来源根路径明确诊断卷未挂载时，显示灰色完整 S；普通等待、其他目录或文件问题不置灰。

## 6. 持久化和兼容性

- schema 当前为 v11，不为上述运行时分类增加文件状态；迁移必须事务化并保留旧库；
- `SourceIssue` 的 `summary`、`detail`、`kind` 分开保存语义；detail 不进入首行 UI；
- `EngineSnapshot.waitingSources` 已使用 `SourceIssue`。`waitingSourceSummaries` 是给已更新到
  新框架版本、但只需要人话摘要的迁移访问器；它不能让未重新编译的旧客户端继续使用已改变的
  `waitingSources` 类型。新增代码应直接读取 `SourceIssue`；
- 成功历史、来源停用/移除关系和 Photos 未确认提交不得因刷新失败而清空；
- Photos 与 SQLite 没有联合事务。查询不到、超时或进程崩溃不能单独证明没有提交。

## 7. 接手开发时的最小验证矩阵

任何修改扫描、调度、提示或存储的 agent 至少运行：

1. 目录 deferred：`scan_run` 无失败、无错误日志，`deferred = true`；
2. 元数据 deferred：同上，且不建立错误文件记录；
3. stamp deferred：文件仍为 pending，retry 字段不变，`retryPending = 0`；
4. 单文件错误：其他文件继续，来源不进入 source recovery backoff；
5. 混合来源失败/deferred：两套 deadline 互不覆盖；
6. Photos 授权失败、数据库失败、日志失败：文案和全局图标类别正确；
7. 退役来源历史、ARW/XMP 排除和通知摘要不回归。

测试必须使用临时目录、临时 SQLite 和注入的 fake gateway/reader。不得启动生产应用、访问生产
Photos 或依据生产数据库路径扫描媒体。当前 main 的基线为 commit `259d990`，核心测试数量以
当前构建实际输出为准；最近修复在 167 项核心测试上通过。

## 8. 变更规则

如果后续要增加真正的新文件状态、改变 deferred 的持久化含义、改变重复判定或允许 Photos 删除/覆盖，
必须先更新本文和产品设计，并新增迁移/验收说明。不要只在 UI 文案或测试 fixture 中改变语义。
