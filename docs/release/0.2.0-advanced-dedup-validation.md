## P11 per-change inventory and measurement boundary

P11 builds on the reviewed `sqlite-exact-f32-v1` query backend and metadata-only publication. A live event is one context-bound, continuous Photos generation interval containing its complete changed/deleted ID sets. It queries only those changed IDs, atomically applies affected representation/task/exclusion facts and a bounded global publication/checkpoint update, and waits for the target generation's acknowledged ready token. Empty continuous events also advance the barrier. Gaps, overflow, partial/missing ID results, nonincremental changes, races, or unknown scope fall back to a complete inventory. Startup/recovery and the existing 30-minute inventory remain.

Schema v5 stores a lightweight exclusion asset set in the same database. v3/v4 migrations preserve file/success/unknown history and existing vectors; v4 exclusion facts start empty and require inventory completion before publication. Full inventory uses temporary eligible representation keys; exclusions cannot preserve old candidate rows. Unchanged representation/task/exclusion rows are not rewritten. Publication generation is separate from task issuance, and task completion validates the persistent task, issuance, full descriptor, fingerprint version and context. Zero/negative/future issuance remains invalid. A delete followed by a same-revision reinsertion invalidates the previous task even when those events coalesce.

Known work granularity: the native adapter conservatively invalidates both representations of an asset reported changed. It does not yet carry `assetContentChanged == false` into persisted descriptor reuse and does not claim metadata-only zero inference or selective original retention for a native edit. Reliable unchanged full-inventory rows and unaffected asset tasks remain reusable. Image-only catalog scope is unchanged; a broad candidate event containing a non-image ID falls back to full inventory rather than inventing a new exclusion category.

The existing scale test now measures five edit/add/delete samples each through real coordinator delta handling, with verified token/Photos generation/count endpoints and P50/P95/P99. It separately reports query-only latency, cached/source preparation, synthetic seed and initial publication, unchanged full inventory, restart, and the largest fixture's 60-second idle footprint/RSS and resume query. These are temporary synthetic SQLite vectors, fake Photos, and actual local model work—not a real 100k Photos library, iCloud traffic, or cold physical disk benchmark.

Resource measurements use an XCTest-only VFS wrapper limited to the named fixture database and SQLite sidecars. All file/locking/mapping results are forwarded. VFS requested reads/writes/mmap fetch ranges and process `proc_pid_rusage` accounting are distinct; neither proves NAND traffic or SSD wear. Table-write counts come from a separate fixture-trigger audit pass. Triggers are removed before resource/idle measurements; query zero writes does not imply whole-import zero writes. The system SQLite's unsupported auto-extension instrumentation attempt is retained as failed local evidence and is absent from the shipped/test implementation.
